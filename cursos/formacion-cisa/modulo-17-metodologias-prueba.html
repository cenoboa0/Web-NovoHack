Metodologías de prueba de sistemas

Antes de que un sistema nuevo o modificado llegue a producción, debe probarse exhaustivamente. Este módulo recorre las clasificaciones de pruebas, desde la prueba unitaria hasta la aceptación final, los distintos tipos de prueba especializados, y los dos enfoques —ascendente y descendente— con los que se puede organizar todo el esfuerzo de pruebas.

≈20 min de lectura De la prueba unitaria a la aceptación del usuario

1 Clasificaciones de pruebas

Las pruebas determinan que se hayan validado los requerimientos del usuario, que el sistema esté funcionando como se anticipó y que los controles internos trabajen como se pretendía. Se organizan en cuatro grandes niveles, cada uno más amplio que el anterior:

Prueba unitariaUn programa o módulo concreto
→
Prueba de interfaz/integraciónConexión entre componentes
→
Prueba del sistemaEl sistema completo
→
Prueba de aceptación finalDurante la implementación
NivelQué evalúa
Prueba unitariaPrueba la lógica del programa con un programa o módulo en particular; garantiza que la operación interna funciona conforme a la especificación, usando casos de prueba centrados en la estructura de control del diseño procedimental.
Prueba de interfaz o integraciónPrueba de hardware o software que evalúa la conexión de dos o más componentes que trasladan información de un área a otra.
Prueba del sistemaSerie de pruebas diseñadas para asegurar que los programas modificados, objetos, esquema de base de datos, etc., que colectivamente constituyen un sistema nuevo o modificado, funcionen de manera apropiada.
Prueba de aceptación finalPruebas del sistema que se llevan a cabo durante la fase de implementación y que aplican la metodología de aseguramiento de calidad (QA) de la organización.

2 Pruebas de aceptación final: QAT frente a UAT

Dentro de la aceptación final conviven dos pruebas complementarias, con propietarios y enfoques distintos:

Pruebas de aseguramiento de la calidad (QAT)

Se enfoca en los aspectos técnicos de la aplicación. Verifica que la aplicación funcione como se documentó mediante pruebas del diseño lógico y la tecnología misma. Garantiza que la aplicación cumpla con las especificaciones técnicas documentadas y los entregables. Implica una participación mínima del usuario final y la realiza el departamento de TI.

Pruebas de aceptación del usuario (UAT)

Se enfoca en el aspecto funcional de la aplicación. Se asegura de que el sistema esté listo para la producción y que satisfaga todos los requerimientos documentados. Se realiza en un ambiente seguro de pruebas que imita lo más posible al de producción. Las pruebas se escriben desde la perspectiva del usuario y las realizan conjuntamente el departamento de TI y el usuario final.

3 Otros tipos de pruebas

Tipo de pruebaDescripción
Alfa y betaLa prueba alfa se realiza en una versión temprana solo por usuarios internos de la organización que desarrolla el software (es una forma de prueba de sistemas). La prueba beta, una forma de UAT, involucra a un número limitado de usuarios externos con exposición al mundo real.
PilotoPrueba preliminar enfocada en aspectos específicos y predeterminados de un sistema, como una prueba de concepto.
Caja blancaUtiliza el conocimiento de la implementación subyacente de un programa/módulo y los intervalos del código para verificar su comportamiento esperado.
Caja negraSe centra en la funcionalidad de la aplicación o producto y no requiere el conocimiento de los intervalos del código.
Función/validaciónPrueba la funcionalidad del sistema contra los requisitos detallados, para garantizar que el software se construyó de acuerdo con los requisitos del cliente.
RegresiónProceso de volver a ejecutar una porción de un escenario o plan de pruebas para asegurar que los cambios o correcciones no hayan introducido nuevos errores.
ParalelaProceso de introducir datos de prueba en dos sistemas —el modificado y un sistema alternativo, posiblemente el original— y comparar los resultados.
SociabilidadConfirma que el sistema nuevo o modificado puede operar en su ambiente sin impactar de manera adversa a los sistemas existentes.

4 Enfoques de prueba y prueba de integridad de los datos

Los dos enfoques principales para organizar el esfuerzo de pruebas de software son:

  • Ascendente: comienza con unidades individuales y trabaja en dirección ascendente hasta que se haya realizado una prueba completa del sistema.
  • Descendente: comienza a probar el sistema completo y trabaja en dirección descendente hasta llegar a las unidades individuales.

Además de probar la funcionalidad, es necesario verificar la integridad de los datos en una base de datos:

  • Pruebas de integridad relacional: rutinas de validación de datos realizadas a nivel de elementos de datos y de registros.
  • Pruebas de integridad referencial: definen la existencia de relaciones entre entidades en diferentes tablas de una base de datos, que debe ser mantenida por el DBMS.

5 El rol del auditor SI durante las pruebas

  • Revisar el plan de prueba, los informes de errores, la documentación del usuario final y los procedimientos utilizados, para asegurarse de que estén completos y sean precisos.
  • Efectuar una reconciliación de los totales de control y de los datos convertidos.
  • Verificar el procesamiento cíclico y los informes críticos para mayor precisión.
  • Entrevistar a los usuarios finales del sistema para verificar si entienden los nuevos métodos, procedimientos e instrucciones de operación.
  • Verificar que la seguridad del sistema funcione como se diseñó.
  • Revisar los resultados de las pruebas paralelas y las pruebas de aceptación del usuario.
  • Revisar los planes de las pruebas de unidad y del sistema para determinar si se planifican y realizan pruebas de los controles internos.
  • Revisar las pruebas de aceptación por parte de los usuarios y asegurarse de que el software aceptado ha sido entregado al equipo de implementación; el proveedor no debería poder reemplazar esta versión.
  • Revisar los procedimientos utilizados para registrar y hacer seguimiento del reporte de errores.
Punto de examen frecuente: las tareas de prueba que exigen conocer la lógica interna del programa (como especificar la lógica del programa u optimizar el rendimiento) NO son apropiadas para que las realicen los usuarios finales; ellos deben enfocarse en probar la salida del sistema desde su propia perspectiva funcional, como en la UAT.
